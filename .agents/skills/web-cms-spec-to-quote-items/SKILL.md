# 網站 / CMS 專案：規格釐清 → 報價項目與描述

把專案的既有材料，轉成兩份可交付物：

1. **規格釐清文件（初步規格表）** — 範圍、內容模型、排除項、相依項與「待確認假設清單」，每個範圍項有 `SCP-ID`。
2. **報價項目與描述清單（handoff）** — 從規格轉出的對外「項目 + 描述 + 驗收依據」，每項追溯 `SCP-ID`。**這份交棒給另一支報價系統 skill 定價**。

> **本 skill 的邊界**：只做到「項目與描述」為止。**不定價、不算人天、不算成本、不出 HTML 報價單** —— 那些由報價系統 skill 負責。
>
> **為什麼項目要做得這麼結構化**：報價單未來是**撰寫 speckit 功能規格的基礎**。每個報價項目 → 一個（或一組）speckit feature；項目的「描述要點」→ 規格的行為描述，「驗收依據」→ 規格的 acceptance criteria。所以項目與描述必須乾淨、可追溯、可獨立驗收。

本 skill 對應 `planning/03-scope-and-solution.md`（範圍）的操作流程；定價與商業條件屬於 `planning/04-estimate-and-quotation.md` 與報價系統 skill 的範疇，本 skill 不碰。

## 鐵則

- **不腦補**：材料沒給的資料，一律標 `[NEEDS CLARIFICATION]`，收進「待確認假設清單」，不自行翻譯成功能。
- **模糊語句原樣保留**：「後台要好用」「要能自己改版面」→ 變成待確認問題，不要直接寫成項目。
- **範圍先於項目**：每個報價項目都必須對應一個 `SCP-ID`；找不到對應範圍時，先補範圍，不得直接加項目。
- **商業規則是一等公民（雙向覆蓋）**：跨頁面／跨模組的邏輯不變量（互斥、綁定、地區別、狀態流轉，如 iMin↔Zero、雙地區商品組合）一律在規格 §4A 獨立登記 `BR-ID`，**不可只埋進某個項目的描述句子**。轉報價時要做**反向覆蓋**：規格有 N 條 BR，報價的「商業規則覆蓋」表就要 N 條、逐條映射項次，數量對不上代表有規則流失。光靠「工項→SCP」正向對應擋不住「規則沒人做」。
- **主動偵測材料衝突**：材料常互相矛盾，不得腦補選一邊，一律標待確認。至少檢查三類：①客戶文件 vs 對話（例：文件寫「多國合規」但窗口說「只做台美」）②頁面文案 vs 實際整合（例：頁面寫 Authorize.Net，實際串 Converge）③現況實測／audit vs 客戶假設。
- **區分「可定範圍」與「可精算」**：範圍結構定了就能列項目；但文件引用卻未附的**主數據**（價目表、品項清單、功能對照矩陣）是**硬阻塞** —— 它決定頁數與元件複雜度。缺主數據時，對應項目標「規模待定（吃主數據）」，並在待確認清單以最高優先標出。這個訊號要傳給報價系統 skill，讓它知道哪些項目還不能精算。
- **不定價**：不要在本 skill 產出金額、單價、人天、成本、毛利、稅額。相對規模（S/M/L/XL）可作為給報價系統 skill 的提示，但不是價格。
- **繁體中文**：所有交付文件用繁中；ID、檔名、程式碼與必要技術名詞保留英文。

## 流程

### 步驟 0：證據優先收件與完成度評分（不要求填滿檢核表）

**步驟 0.0（前置分支）：先問有沒有 reference／現有網站可評估。**

在倒證據之前，先問使用者一句：**「有沒有 reference 網站或現有網站可以參考評估?」**

- **有** → 先跑 `web-experience-audit` skill（已全域安裝）對該站產出稽核成果：`report.html`（給人看）＋ `pages.json`（事實層）＋ `analysis.json`（判斷層）。**把 `pages.json` 當 §1 現況盤點的最強證據**帶回下方證據對映（見 `references/evidence-source-map.md` 首列），再繼續評分。`analysis.json`（判斷層）僅供參考——規格結論以事實層為準，不拿 audit 的主觀評價當範圍依據、不腦補。
- **沒有** → 直接用客戶文件／對話跑證據對映；§1 現況多半標「未涵蓋」或待確認。

> **交棒是「資料交棒」非「函式呼叫」**：audit 寫出檔案、本 skill 去讀。步驟 0 先檢查約定落點是否已有既存 `pages.json`／`report.html`，**有就直接採用、不重跑 audit**。

**檢核表是「覆蓋率評分標準」，不是「問卷」。** 不要叫人從頭填 32 格 —— 真實世界的資料散在既有產物裡。

1. **先倒證據**：網站體驗 audit 報告、客戶原始文件（RFP／改版文件）、第三方（如金流）技術文件、往來對話與訊息，全收進來。
2. **自動對映檢核表**：用 `references/evidence-source-map.md` 把每份材料對到它覆蓋的檢核表格，逐格標 `✓ 已覆蓋` / `△ 部分` / `✗ 缺`。
3. **算完成度、套閘門**（改版案 32 項／全新案 24 項）：
   - **≥ 80%** → 可直接往下列項目。
   - **60–79%** → 可列項目，但規格釐清文件必須列「待確認假設清單」，並在項目清單標出受影響項。
   - **< 60%** → **先停下**，建議需求訪談；產出「缺漏清單＋訪談題綱」而非硬列。
4. **只對「缺、且會影響範圍或計價」的格產生精準追問**（通常 6–10 題，而非 32 格）；其餘缺口進待確認假設。每個缺漏標處理方式：`待確認假設` / `排除條款` / `訪談追問`。
5. 收到答案後，回頭關掉對應的待確認格，並**重新偵測是否引入新衝突或新項目**（例：客戶答「要雙語」會讓語系獨立成項目、答「自建後台」會把案子從官網抬升為電商平台）。

> 完全沒有既有產物時，才把 `references/intake-checklist.md` 交給對方蒐集；但通常 audit + 客戶文件已能覆蓋一半以上。

### 步驟 1：產出規格釐清文件（初步規格表）

以 `references/spec-sheet-template.md` 為骨架，把材料轉成規格：

- **內容模型是 CMS 成本核心** — 內容類型、關聯、多語、維護角色、更新量體、媒體資產，直接決定後台項目與權限設計。逐一落成 `SCP-ID`。
- **邊界條件 → 排除表與相依表** — 第三方整合由誰申請帳號與付費、主機／部署歸屬、資料遷移範圍、SEO 轉址、無障礙／資安／法遵、維護合約，全部要落地。
- 每個範圍項標優先級（Must／Should／Could）與**驗收方式（可觀察成果，不是工時）** —— 這個之後會變成 speckit 的 acceptance criteria，寫清楚。
- **把橫切商業規則抽出來獨立登記 §4A（BR-ID）** —— 材料／訪談每出現一條互斥、綁定、地區別或狀態流轉邏輯，就開一列。這是規則的出生地，下游報價與 speckit 都靠它逐條回溯；埋在 SCP 描述裡的規則會流失。
- 檔尾附「待確認假設清單」，逐項寫：假設內容、影響（範圍／時程）、要向誰確認。

輸出後，把重點回報給使用者確認再進步驟 2；範圍是項目清單的地基，先對齊。

### 步驟 2：把規格轉成「報價項目與描述」清單（本 skill 的主產出）

以 `references/quote-items-template.md` 為格式，把 `SCP-ID` 範圍轉成對外可讀的項目。每個項目包含：

| 欄位 | 說明 |
|------|------|
| 項目名稱 | 對外可讀的工項名稱（可合併多個 SCP，但仍列出對應 SCP-ID） |
| 描述要點 | 條列這項在做什麼（→ 未來 speckit 的行為描述） |
| 對應 SCP-ID | 追溯回規格釐清文件 |
| 驗收依據 | 可觀察的完成標準（→ 未來 speckit 的 acceptance criteria） |
| 交付階段／分類 | 例：設計／前台／後台／金流／SEO／上線（供報價系統 skill 分組） |
| 相對規模（選填） | S/M/L/XL，給報價系統 skill 當估算提示，非價格 |
| 計費性質 | 一次性／持續性（供報價系統 skill 判斷） |
| 待確認註記 | 若吃主數據或有衝突未決，標「規模待定（吃主數據）」或引用待確認編號 |

原則：
- **對齊實際報價單格式**：報價單欄位是 **項目 ｜ 說明 ｜ 人天數 ｜ 金額**，依交付階段分組（A. 前端開發 / B. 後端 CMS / C. 金流 / D. SEO・上線 / E. 專案管理）。本 skill 只填「項目」與「說明」，人天數與金額留空給定價方。SCP-ID 與驗收依據帶在 handoff 檔供追溯，不上報價單。
- **說明要具體、可實作、可驗收**：依 `references/quote-items-template.md` 的「說明撰寫風格」—— 前綴標明假設（如「依客戶提供之設計稿完成…前端實作」）、點名具體頁面／元件、相關商業規則寫進說明並標註 BR-ID（如「iMin↔Zero 限制（BR-001）」）、串接來源寫清楚、頁數放副標、中英混用。
- **每個 SCP 逐面向展開，別讓一對多變成漏項**：一個 SCP 常要同時落成前端多頁＋後端模組＋金流＋SEO 好幾個工項。轉項目時對每個 SCP 逐一問「**前端頁？後端？金流？SEO？**」，每個需要的面向各自列項。**最容易漏 B 前端**——會員（註冊/登入/會員中心）、購物車與結帳、訂單查詢這類橫跨前後端的功能，前端呈現常被後端項目一句話吞掉。「報價項→SCP」正向對應擋不住這種漏（缺的項根本沒被列出來），必須靠下面的反向矩陣。
- **SCP × 交付階段反向覆蓋，不靠正向對應把關**：把 quote-items 的「SCP × 交付階段覆蓋矩陣」逐格填——SCP 當列、交付階段（A設計/B前端/C後端/D金流/E上線）當欄，格子填項次。**空格必須交代**（「—」不需要／「⚠️補」漏了），有任何 ⚠️ 不得交棒。這跟 BR 覆蓋表是同一種紀律：SCP 顧「範圍不漏」，矩陣顧「範圍內每個面向不漏」。核對 B 前端欄時拿 audit 的 sitemap（現況每個 URL）＋ RFP 新增頁面掃一遍。
- **商業規則另建覆蓋表，不靠描述把關**：把規格 §4A 的每條 BR 填進 quote-items 的「商業規則覆蓋」表並映射項次，逐條核對數量對得上。說明裡引用 BR-ID 是輔助，權威清單是覆蓋表——否則沒有明顯歸屬頁的規則（如雙地區商品組合）會漏掉。
- **釐清設計歸屬**：若客戶提供設計稿，說明用「依客戶設計稿…前端實作」並把「介面設計」列入排除；若設計要我方做，另立「設計」項目，別混進前端實作。
- **每個項目都能追溯 SCP-ID，且都有驗收依據** —— 這是它日後能變成 speckit 的必要條件。
- **雙語與雙地區是兩回事，分開處理**：雙語（語言切換）獨立成前端項目（如「多語系切換」自成一條），不要被一句「多語系」帶過；雙地區商品組合（美/台目錄／計價／金流不同）是**商業規則**，登記於 §4A 與覆蓋表，切勿把它當成語言問題壓進「多語系」項目。
- **明確排除項另立一區**（不遷移、不含文案翻譯、不含設計稿、不含第三方 API 串接等），供定價方寫進報價備註。
- 不要在這裡定價；把「規模待定（吃主數據）」訊號一併交棒。

### 步驟 3：交棒給報價系統 skill，並保留 speckit 可追溯性

- 把步驟 2 的項目清單交給**報價系統 skill** 進行定價與正式報價單產出。若該 skill 有指定的輸入欄位／格式，依它的 schema 對齊 `references/quote-items-template.md` 的欄位。
- 保留三層可追溯鏈：**規格釐清（SCP-ID）→ 報價項目 → 未來 speckit feature**。報價單定案後，每個項目可據此開 `/speckit.specify`（描述要點→spec 行為、驗收依據→acceptance criteria）。
- 把「待確認假設清單」與「規模待定（吃主數據）」的項目一併標明交棒，讓定價方知道哪些還不能鎖。

## 交付檔案位置與命名

- 規格釐清文件：`{客戶名}-規格釐清-{YYYYMMDD}.md`
- 報價項目與描述清單：`{客戶名}-報價項目-{YYYYMMDD}.md`

正式案件（專案執行模式）中，優先把範圍直接填進 `planning/03-scope-and-solution.md`，並在 `planning/decision-log.md` 記錄對應決策；定價與 G2 由報價系統 skill 與 `planning/04-estimate-and-quotation.md` 負責。

## 交付前檢查

- [ ] 完成度已評分，閘門判定已寫明；< 60% 時已改走訪談建議而非硬列。
- [ ] 每個範圍項可追溯至材料或客戶原文；模糊語句已轉為待確認問題而非項目。
- [ ] 材料衝突已偵測並標待確認，未腦補選邊。
- [ ] 每個報價項目都有 `SCP-ID` 與**驗收依據**（可日後轉 speckit）。
- [ ] **SCP × 交付階段矩陣無 ⚠️**：每個 SCP 逐欄（A設計/B前端/C後端/D金流/E上線）填項次，空格已交代「—」或補項；橫跨前後端的功能（會員／購物車／結帳／訂單）B 前端欄有項、未被後端吞掉；已拿 audit sitemap＋RFP 新增頁核對前端頁面完整性。
- [ ] **商業規則雙向覆蓋**：規格 §4A 的每條 BR-ID 都對應到 ≥1 報價項次，「商業規則覆蓋」表條數與 §4A 一致（數量對得上、無孤兒）。
- [ ] 雙語（語言）已獨立成項目；雙地區商品組合已列為 §4A 商業規則，未被壓進「多語系」。
- [ ] 明確排除項已獨立列出。
- [ ] 吃主數據或未決衝突的項目已標「規模待定」，並在交棒時標明。
- [ ] **未在本 skill 產出任何金額／單價／人天／成本**（定價由報價系統 skill 負責）。
